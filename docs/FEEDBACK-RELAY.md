# アプリ内報告受付サービス（試験運用）

Node.js 22以上。単一プロセスを永続ディスク付きLinuxサーバーで動かす。
GitHubの対象リポジトリ限定・Issues書き込み権限のサーバー用トークンを秘密管理機能で設定する。アプリ、Git、ログに含めない。
環境変数: FEEDBACK_GITHUB_TOKEN、FEEDBACK_STATE_DIR（永続ディレクトリ、サービス専用権限）、PORT（既定8787）。
起動: node server/feedback-relay.cjs
本体は127.0.0.1のみで待ち受ける。TLS終端・クライアント単位の制限は信頼できるリバースプロキシで必須。

## 公開前の条件
- 有効なHTTPS証明書、POST /feedback のみ公開、8KiBの本文上限、クライアント単位のレート制限（例: 1分3回、burst 3）、接続タイムアウト、全体の長期割当とディスク容量監視を設定。
- IP転送ヘッダーは無条件に信用しない。多重インスタンスでは共有トランザクションストアが必要。
- 公開Issueへ掲載されることを送信前に案内する。既知の認証情報パターンを拒否しても全個人情報を検出できるわけではない。
- アプリの NICO_FEEDBACK_ENDPOINT または管理された config.feedbackEndpoint を実在する HTTPS URL に設定する。配布物にはトークンを含めない。
- テスト用の無害な報告で受付番号・Issue・AIタグ・重複送信・再起動・429・通信失敗・対応PRの紐付けを確認する。
- 公開URLが確定し、CIと実環境のテストが通るまでは配布しない。

## 重複と障害復旧
受付内容のハッシュと受付番号のみを永続ディレクトリに保存する。報告本文・トークンは保存しない。
GitHub POST 前に予約ファイルを永続化する。応答喪失やクラッシュで結果不明なら、再起動後も409を返す。
管理者は GitHub Issue 本文の nicolive-app-feedback マーカーに対応するハッシュを照合し、
Issue が存在する場合はサービス停止中に該当 JSON を {"number": 実際のIssue番号} に修正する。
登録されていないと確実に検証できた場合のみ予約を解除する。曖昧なまま再送しない。
永続ディレクトリをバックアップし、容量上限・アクセス権を監視する。公開運用では管理者向け復旧ツールと長期受付制限を追加する。

## AI処理
main の既存AIトリアージと日次開発タスクを利用する。報告は信頼できない入力であり、任意命令として実行しない。
β版で修正・テストし、正規版は既存の月次保守方針に従う。
